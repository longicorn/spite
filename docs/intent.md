# 確率的なソフトウェア納期予測の設計

## 1. 目的

ソフトウェア開発の納期を単一の日付として断定したい/求められるプロダクトが存在する。
工数/人月を考慮するプロダクトの場合もこれに類似するものと考える。

これよりはより良い予測を立てるために過去には以下のような方法があげられている
- COCOMO / COCOMO II
- Putnam–Norden / SLIM
- Function Point / COSMIC
- SEER-SEM
- Littleの法則・待ち行列理論
- 信頼性成長モデル
- Reference Class Forecasting
- Bayesian Estimation
- Monte Carlo Forecasting

これまで確認したツールの予測方法は、主に以下の2通りとして整理できる。ただし、これは見積もり・予測手法全体を網羅する分類ではない。

| 系統 | 予測の考え方 |
| --- | --- |
| 計画・見積もり系 | 工数、人数、稼働率、規模、能力から納期を組み立てる |
| フロー予測系 | 過去の完了数・サイクルタイムから将来の完了確率を推定する |

これまで確認したアジャイル向けモンテカルロツールには、現在のチームのスループットを再サンプリングして予測するものがある。

Walker Royce氏が紹介する「システムの納期とは確率分布である」という捉え方を、本ツールの中心に置きたい。既存の確率予測手法とも共通する考え方だが、今回求めるのは、開発初期から分布を仮に置き、その種類や形を選択・調整して継続的に更新できる操作である。
この操作を手軽に行えるツールは、これまでの調査では確認できていない。
よってこの考え方を元にプロダクトの納期予測を行うシンプルなソフトウェアを提案する。
この方法を用いて「指定日までに開発が完了する確率は何%か」を、採用した分布と仮定に基づいて提示したい。現場の経験や判断を初期入力として使い、その後の実績と比較することで予測の妥当性を検証していく。

今回の私のアイディアはこの確率分布を元としてこう考えてみる

- 過去の類似案件(のデータが存在していれば)ではどのような完了期間分布だったか? 
- 新しい機能はそのどの分布に近いか?
- 現在の状態によって、その分布はどう変形するか?


## 2. 確率分布の決定
[システムの納期とは確率分布だ](https://www.publickey1.jp/blog/09/post_56.html) では具体的な確率分布は何かを示しておらずblogは対数正規分布ではないかと推測している。
ベント・フリウビヤ（Bent Flyvbjerg）教授とダン・ガードナー（Dan Gardner）の共著 `How Big Things Get Done` や、フリウビヤらのプロジェクト研究を着想の背景としている。会話で確認した[ITプロジェクト研究](https://arxiv.org/abs/2210.01573)は、コスト超過にべき乗則的な重いテールが観測されると報告している。これを完了期間にも適用することは、本ツールで検証したい仮説であり、納期が同じ分布に従うと確認されたわけではない。
ここから私は、進捗が厳しいプロダクトでは対数正規分布とParetoまたはGPDを組み合わせたスプライス分布の採用がより適切になる可能性を提示したい。
また、通常進行と再計画後の進行など、異なる状態が想定される場合には混合分布を候補とする。複数の山が現れる可能性もあるが、山の数だけで納期遅延の多発や完成困難を判断することはできない。これらの分布と開発状態の対応は、実験しながら検証する仮説として扱う。

プロジェクト開始時の初期の確率分布の選択は以下のようなのが考えられるだろう

- 実績分布の再サンプリング
- 対数正規分布
- 対数正規分布とParetoまたはGPDを組み合わせたスプライス分布
- Weibull分布
- Gamma分布
- 複数の確率分布による混合分布

実際にはこれらの分布を何らかの係数を適応して分布を変形させた形になると思われる

実際の運用としては過去実績データでは計算のみで済むだろうし、現在進行系のプロジェクトには典型的にはアジャイル/スクラム開発でいうスプリント毎に実績を計測して計算を毎回行い修正していくイメージとなるだろう。

## 3. 納期予測とアルゴリズム

### 係数

係数をどのように計算に用いるかはまだ不明だがそれは実験しながら決めていけばよいと思われる。
ただ何を係数にするかも難しいが以下のようなものを現時点では想定している。

#### 定量的なデータ
- チーム人数、加入・離脱の時期、教育に必要な時間、調整負担など。ブルックスの法則はこれらの負担に着目する参考とし、納期や補正係数を直接算出できる式としては扱わない。各情報が予測に与える影響は実験で検証する。
- GitHubのIssue, PRや類似データ
- JIRA等の管理ツール


私の経験では、日本でスクラム開発が急速に普及した時期には、ストーリーポイントやフィボナッチ数列を使う見積もりが、スクラムと一体のものとして広く教えられていた。その認識が更新されず、今も必須と捉えられている場面がある。しかし、これらはスクラムの必須要素ではなく、目的に応じて採否を判断できる。本ツールではストーリーポイントを利用せず、完了期間の確率分布とその更新を予測の中心に置く。

参考: [ケン・シュエーバーが意図的にスクラムから除外した項目](https://scrummaster.jp/things-ken-schwaber-intentionally-omits-from-scrum/)

#### 定性的なデータ
GitHub, Notion, Slackなどのコミュニケーション情報が代表的なデータとなる。
これらのデータを定量的な値へ変換する方法はこれまで難しかったがLLMの登場により例えば項目ごとに5段階評価を行う程度なら一定の信頼性とともに利用できるだろう。ただしプロンプトやモデルによっても大幅に変わるので注意する必要がある

### 入力データ
既に述べたように過去実績データがある場合githubのIssue,PRやNotion等による記録から開発にかかった日数等が利用できる

過去実績データがない場合は、チームの状況や経験に基づいて仮の分布を置く。初期候補として対数正規分布を用い、極端な遅延を想定する場合はスプライス分布も試す。ただし、チームの状態だけで適切な分布が確定するわけではなく、選択理由を仮説として記録する。

分布の種類だけでは、何日程度の開発なのかは決まらない。そのため、データがない場合も、基準となる期間と大まかな幅を入力できるようにする。例えば「中央値とP90相当の期間」や「基準期間と不確実性の段階評価」からパラメータを設定する。段階評価を幅へ変換する規則も暫定的なものとして扱う。概算・三点見積もりや経験則も入力の候補とし、初期値とその前提を保存して実績で更新する。

### 出力データ
出力は単一の納期ではなく、少なくとも以下を提供するのが良いだろう

- 確率分布グラフ: 楽観・基準・悲観の3シナリオ
- 各シナリオのP50・P80・P90
- 各シナリオの目標日達成確率

3シナリオは、例えば依存先の回答が早い・通常・大幅に遅いといった前提の違いを表す。それぞれの前提に応じて係数や分布を設定し、その分布からパーセンタイルと達成確率を計算する。「基準シナリオ」は分布の最頻値を意味しない。

P50・P80・P90は一つの分布内の累積確率に対応する値であり、3シナリオとは区別する。モンテカルロ法は各シナリオの計算に利用できるが、試行結果を3つに分けるだけで前提の異なるシナリオが作れるわけではない。

## 4. 実装
初期開発はCUIで十分と思われる。
単独でJiraのようなソフトウェアにするのは不要かもしれない。
Jiraのようなツールに組み込むAPIとかにするのが良いかもしれない。

初期化
$ spite init

開発開始
$ spite start <name>
ここで分布決めとかできると良い

過去実績データの取り込み
$ spite analyze <name> <csv>
$ spite analyze <name> --issue 120
$ spite analyze <name> --pr 123

現在スプリントの更新
$ spite calculate <name>

特定開発の納期予測
$ spite predict <name>

### 予測方法の検討
まずは、確率分布をどう適応してどう計算するか、の手法探求が最初に行うべきことで当面ここに集中する

過去の開発データを利用して仮想スプリントで再現し、分布を調整して予測方法を検討するのが良いと思われる
