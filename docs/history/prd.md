# Product Requirements: Local Git History

[日本語版](prd.ja.md)

`spite history` reports the local Git history reachable from the current branch's HEAD after a specified ancestor commit or tag. It is intended for a branch representing a released state; Spite does not verify that a release occurred. A checked-out branch and an ancestor `--base` are required. `--base` accepts a branch name such as `master`, a tag, or a commit ID. The range is `base..HEAD`: commits reachable from HEAD but not from base, including merged branch commits. Base and its reachable history are excluded. Branch tips can move, so use a release tag or commit ID for a stable starting point. If base and HEAD are the same, the range is empty.

For a release branch containing multiple merged feature branches, check out the release destination and set `--base` to an ancestor before the merges, such as the previous release tag. Do not use `--base` to select an individual merged branch: its tip and ancestors are excluded from the range. `--base main` is empty when `main` is the current HEAD.

Each non-merge commit is one observed work unit. Merge commits are reported separately as joins. The report displays the parent graph, counts visible forks, and identifies a linear observed history or the presence of parallel paths. This describes Git topology, not proven task dependencies, branch names, or simultaneous work. Squash merges, rebases, cherry-picks, and unavailable or shallow history may obscure the original development structure.

The observation span is measured from the earliest to the latest committer timestamp among commits in range, in calendar days. It is not measured work duration: work may start before the first commit, timestamps may be edited, and the span includes weekends, holidays, and inactivity. Empty ranges have no span. `--days-per-period` optionally converts this span to approximate periods using a simple multiplier.

With `--output`, a report and versioned snapshot are saved under `history/<run-id>/` in the selected root. Without it, Markdown is printed. Optional `--forecast-id` loads a saved forecast from the same root; `--forecast-kind simulate` (default) or `predict` selects its type. Comparison requires `--days-per-period` and a nonempty range. The report displays the observed span beside the Nominal P50/P80/P90 forecast as a proxy, not an actual-duration evaluation. A continued simulation uses its total forecast including elapsed periods.

Display report timestamps in the runtime local timezone as readable dates and times, using the format `YYYY-MM-DD HH:MM:SS(TZ)` with the timezone abbreviation, or the UTC offset if no abbreviation is available. Preserve timezone-aware timestamps in the snapshot and calculate elapsed time from actual instants. For the observed timestamp span and the two additional periods below, display each endpoint and duration as a separate list item, followed by explanatory text in a separate paragraph.

## Periods outside observed development commits

The user may optionally supply the overall development start date and time with `--development-start`, as an ISO 8601 timestamp with a timezone offset (for example `20240101T090000+0900`). When the selected range contains commits, report the elapsed time from that start to the earliest committer timestamp as a separate pre-Git period, and show it as a distinct task in the observed Git history graph, inserted into the displayed paths from boundary parents to in-range commits. It may include planning and development before the first commit; the first commit timestamp does not establish when coding finished. Require a start no later than the earliest timestamp. If the range is empty, the period is unavailable. This task is not a Git commit or an observed work unit.

Report one release-wait period from the latest committer timestamp of a non-merge commit in the range to the latest merge committer timestamp that is later than it. If either endpoint is unavailable, do not display a duration. Also show a separate waiting task in the observed Git history graph, inserted into all displayed parent paths entering merges at the ending timestamp. Period nodes have dashed borders; commit borders and arrows are solid. The graph legend explains the distinction. Period nodes and their connections are visual groupings, not Git commits or evidence of ancestry or actual work order. Grouping paths can obscure which parent belongs to which commit. This elapsed time is a proxy: approval, release scheduling, further work, and inactivity may all occur during it. Timestamps can be altered, and Git does not establish the reason for the interval. Squash or fast-forward merges may leave no merge commit to measure. Both additional periods use calendar elapsed time and may be converted to approximate periods with `--days-per-period`; they do not change the existing commit timestamp span or forecast comparison.

Future consideration: optionally use `gh` to obtain GitHub approval timestamps as supplementary information. This is not a current requirement.
