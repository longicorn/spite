# プロダクト要件定義書 (PRD): シミュレーションモジュール

[English Version](prd.md)

## 1. ビジョンと背景

ソフトウェア開発の納期予測における従来のアプローチには、主に以下の2種類が存在します。
1. **パラメータ分布による近似（現行 Spite のベースライン）**: プロジェクト全体の工期を単一の確率分布（対数正規分布など）でモデル化し、シナリオ（最善・通常・最悪）の違いを主観的な倍率係数で調整する手法。
2. **決定論的ネットワーク計画（PERT / CPM / 静的モンテカルロ法）**: WBS等を用いてプロジェクトを固定の有向非巡回グラフ（DAG）に分解し、各タスクの所要時間のみを確率変数として乱数シミュレーションする手法。

しかし、実際のソフトウェア開発には **Fog of War（戦場の霧）** とも呼ぶべき構造的な不確実性が存在します。
- **未知タスクの動的発見**: 多くの作業（Unknown Unknowns）や隠れた依存関係は、調査・設計・実装を進めて初めて顕在化します。
- **手戻りと反復ループ**: レビュー差し戻し、仕様の不整合、リグレッション障害などにより、単純な非巡回フローではない循環的な手戻りが発生します。
- **レビュー・承認待ちと外部依存**: レビュー待ち、アーキテクチャ承認、顧客確認、外部API提供待ちなど、エンジニアを増員しても短縮できない非線形な待機時間が存在します。
- **並列化の限界**: 直列依存や合流・統合コストによって、チーム人数と工期の関係はアムダールの法則やブルックスの法則に制約されます。

**シミュレーションモジュール**（`/simulation`）は、**Lane-Model** の構想に基づいた構造的シミュレーションエンジンを提供します。固定グラフや恣意的な分布関数を前提とするのではなく、決定論的な初期構造から発見や手戻りによって実行中の構造を変化させ、リソース制約下での進行をシミュレーションして、共有可能な構造化MarkdownとMermaid図を伴う経験的納期分布を出力します。

## 2. 対象ユーザーと主要ユースケース

### 対象ユーザー
- **エンジニアリングマネージャー / テックリード**: プロジェクトのテールリスクの原因、増員による短縮効果の有無、真のボトルネック箇所を構造的根拠に基づいて説明したいリーダー。
- **アジャイル / スクラムチーム**: スプリントごとに完了実績を固定し、残余の不確実性を再シミュレーションして予測を更新したいチーム。
- **ステークホルダー / 意思決定者**: 最善・通常・最悪シナリオの背後にある前提や妥当性を透明性高く検証したい関係者。

### 主要ユースケース

#### UC-1: 構造的フォワード予測（プロジェクト初期）
プロジェクト開始前に、チームは大まかな前提（規模、不確実性、構造パターン、チーム人数）を指定します。エンジンが決定論的な初期構造から最善・通常・最悪シナリオそれぞれについて数千回の実行をシミュレーションし、経験的なP50、P80、P90工期を算出します。

#### UC-2: 人員配置・ボトルネック感度分析
チーム人数（例: 1名 vs 2名 vs 4名）を変更した際の工期分位点の変化を比較し、直列依存やレビュー・承認待ちによって並列化の頭打ち（サチュレーション）が発生していないかを検証します。

#### UC-3: スプリントごとの再予測（開発途中）
開発中の経過periodと完了タスク数を累計で記録します。把握している残タスク数から新しい仮の構造を生成します。実際の完了済み依存関係や進行中の作業は再現しません。

#### UC-4: Markdown & Mermaid による共有・レビュー
代表的なプロジェクト構造、クリティカルパス、レビュー・承認のボトルネックを表現したMermaidフローチャートを含む構造化Markdownレポートを出力し、GitのPRやWiki上でテキスト差分としてレビュー・共有します。

## 3. 製品スコープと機能要件

### 3.1. CLIインターフェース: `spite simulate`

シミュレーションエンジンは専用のCLIサブコマンドから実行します。

```bash
uv run spite simulate [OPTIONS]
```

#### 主な入力パラメータ
- `--days-per-period`（正の数、任意）：1 periodに相当する概算日数。カレンダーや祝日は計算しません。
- `--pattern` (選択式: `linear`, `parallel`, `complex`, `exploratory`, デフォルト: `complex`): プロジェクトの基本構造テンプレート。
- `--scale` (選択式: `small`, `medium`, `large`, デフォルト: `medium`): 想定されるおおよそのNode規模。
- `--uncertainty` (選択式: `low`, `medium`, `high`, デフォルト: `medium`): 進行中に隠れたNodeや依存関係が発見される傾向の強さ。
- `--rework-rate` (浮動小数点: `0.0` 〜 `1.0`, デフォルト: `0.15`): レビュー後に手戻りが発生する確率。
- `--team-size` (整数, デフォルト: `2`): `--roles` 未指定時における並列アクティブタスクの同時実行上限数。
- `--roles` (文字列, 任意, 形式: `"<role1>:<count>,<role2>:<count>"`): ロール別のリソースプール（例: `"pm:1,dev:2,qa:1"`）。未指定時は `--team-size` がロール制約やスイッチングコストのない均一プールとして機能します。指定時は各ロール専任の人を人数分作成します。
- `--switching-cost` (0以上の数値, 任意, デフォルト: `0.0`): 共有リソースや兼任メンバーが連続するタスク間で異なるロールに切り替える際に発生するオーバーヘッド遅延（period単位）。既定は0（切り替えペナルティなし）。
- `--tasks-per-period`（正の数、既定: `1`）：メンバー1人が1 periodあたりに進めるタスク数の基準。その逆数がタスク期間の最頻値となり、実際の完了数を保証する値ではありません。タスク、発見された作業、手戻りの期間は、この最頻値の0.5〜2倍の範囲とする三角分布から抽選します。レビュー・承認待ちは別の分布を使います。
- `--iterations` (整数, デフォルト: `2000`): シナリオごとのモンテカルロ試行回数。
- `--format` (選択式: `markdown`, `terminal`, `png`, デフォルト: `markdown`): 主たる出力形式。
- `--output`（パス、任意）：実行ごとの`report.md`と`snapshot.json`を保存するルート。PNG形式では`chart.png`も保存します。
- `--continue-from`（実行ID、任意）：保存先ルートから前回のシミュレーションを読み込みます。開始時からの累計`--elapsed-periods`、`--completed-tasks`と、現在把握している`--remaining-tasks`が必要です。残タスクから新しい仮の構造を生成し、完了済みの依存関係や進行中の作業は再現しません。条件は明示的な変更がない限り引き継ぎます。レポートは残期間、合計期間、前回の合計P50・P80・P90を比較します。

### 3.2. 構造的グラフ生成モデル

既定ではパターンと規模が同じなら初期構造は同じです。任意の構造変動を指定すると初期構造も変わり、試行中には発見や手戻りによって実行グラフが変化します。

| パターン | 構造的特徴 | 想定される開発シナリオ |
| :--- | :--- | :--- |
| **直線型 (`linear`)** | 順序通りの直列依存 ($A \to B \to C$) と条件付き手戻り | 障害調査、単一トラックでの段階的リファクタリング |
| **並列型 (`parallel`)** | 高い分岐度 ($A \to \{B, C, D\} \to \text{合流}$) | 独立した複数機能の追加、疎結合なマイクロサービス開発 |
| **複雑型 (`complex`)** | ダイヤモンド構造、段階的合流、レビュー、統合テスト | フロントエンド/バックエンド/DBが連動する一般的な複数レイヤー開発 |
| **探索型 (`exploratory`)** | 高いFog of War、動的Node分解、隠れた依存の頻発 | レガシーコード刷新、未知技術のPoC、ゼロイチの新規開発 |

#### シナリオ別の条件設定
- **最善シナリオ (Best)**: 不確実性が低く（未知Nodeの出現が少ない）、手戻り率が極小（5%未満）、レビュー・承認待ちが最短。
- **通常シナリオ (Nominal)**: 入力指定に応じた標準パラメータ。タスクの所要期間分布は全シナリオで同じで、発見、手戻り、レビュー待ちを変える。
- **最悪シナリオ (Worst)**: 発見確率が1.5倍（上限1）、手戻り確率が高い（25%以上、上限100%）、レビュー・承認待ちが長期化。

---

### 3.3. 離散事象・リソースシミュレーションエンジン

生成されたグラフごとに、リソース制約と依存関係を考慮したシミュレーションを実行します。
1. **Node工数のサンプリング**: 各Nodeの所要工数を、複雑度に応じた分布からサンプリング。
2. **リソースキューイングとロール割り当て**:
   - 既定モード（ロール未指定時）: 実行可能となったNodeに対し、チーム人数（`--team-size`）の枠をクリティカルパス優先度順に均一に割り当て。
   - ロール別配分時（`--roles` またはトポロジ内の `roles` 指定時）: 各Nodeに必要な役割を担当できる人を割り当てます。
   - **複数ロール要求タスク（共同割り当て）**: 複数ロールを必要とするタスク（例: 合同設計やレビュー `roles: [pm, dev]`）は、指定されたすべてのロールの空き枠を同時に確保してから実行を開始。
   - **コンテキストスイッチングコスト**: 兼任リソースや少人数体制において直前のタスクと異なるロールのタスクに着手する際、オーバーヘッド遅延（`--switching-cost`）が加算されます。ロール未指定時はスイッチングコストは発生しません。
3. **レビュー・承認待ち**: レビュー時に待ち時間が発生します。この待ち時間は開発チームの人員枠を占有しません。確率判定により通過するか、上流作業をやり直すかを決めます。
4. **動的発見**: 探索的Nodeの完了時に確率判定を行い、新たな子Nodeや依存関係を作業グラフへ動的に注入。
5. **完了期間の計測**: 全ての終端Nodeが完了した時点の累計periodを、その試行の所要期間 $T_i$ として記録。

---

### 3.4. 出力仕様と構造化 Markdown レポート

`--format markdown` 指定時、Gitでのバージョン管理やPRへの添付に適した自己完結型のMarkdownレポートを生成します。

1. **エグゼクティブサマリ表**:
   - 最善・通常・最悪シナリオごとのP50（中央値）、P80、P90の期間をperiodで示し、任意で概算日数を併記します。
   - クリティカルパスのボトルネック要約（例: 「レビュー・承認待ち時間がクリティカルパスの32%を占有」など）。
2. **Mermaid による構造可視化**:
   - 代表的な仮想プロジェクト構造を Mermaid の `flowchart LR` / `flowchart TD` で描画。
   - クリティカルパス上のNodeをスタイル強調（`style NodeX stroke:#e74c3c,stroke-width:3px`）し、ボトルネックとなったレビューを視覚化。
3. **経験的分布の表現**:
   - シミュレーション標本から算出した分位点テーブル、通常シナリオのP50・P80・P90の説明、Mermaid `xychart-beta`による分布図。結果は仮定に依存し、実際の完了時期を保証しないことも説明します。
4. **アクションにつながる示唆**:
   - 人員配置に関する感度評価（例: 「直列のレビューが支配的なため、人数を2名から4名に増やしてもP80は6%しか短縮されません」等の示唆）。

## 4. 技術アーキテクチャ

### 4.1. モジュール構成

実装は`src/spite/simulation/`にある。`engine.py`は初期構造の生成と実行、`topology.py`はYAMLの検証と下書き生成、`cli.py`はシナリオの実行とレポート出力を担当する。

### 4.2. 性能要件
- 3シナリオ × 2,000試行（20〜50 Node規模のグラフ実行計6,000回）が、標準的な開発マシン上で **5秒以内** に完了すること。
- 試行間の不要な中間実行状態を保持せず、メモリ消費量を最小限に抑えること。

## 5. 対象外事項（Non-Goals）とロードマップ

### Phase 1: MVP（本 PRD の対象スコープ）
- 4つの基本パターン（`linear`, `parallel`, `complex`, `exploratory`）によるグラフ生成。
- チーム人数制約および手戻りループを考慮した離散シミュレーション。
- Mermaid図および分位点表を含む構造化Markdownレポート出力。
- CLIサブコマンド `spite simulate` の提供。

### Phase 2: 途中実績の反映と履歴管理（将来拡張）
- 実際のタスクID、依存関係、進行中の状態を取り込んだ再予測。
- 保存した予測を使った精度の事後振り返り。

### Phase 3: 外部システム連携（将来拡張）
- GitHub / GitLab の Issue グラフや PR レビュー実績を解析し、初期パターンのパラメータを自動校正する連携機能。

## ユーザーが指定する構造

`spite simulate --topology FILE`でYAMLを読み込む。ルートには任意の`roles`マッピング（例: `{pm: 1, dev: 2, qa: 1}`）、`elapsed_periods`（0以上の数値、省略時0）、`tasks`（リスト）を指定する。各タスクは一意な文字列の`id`、文字列の`name`、`kind`（`task`, `gate`, `exploratory`）、`status`（`pending`, `completed`）、任意の`roles`（ロール文字列のリスト、例: `[dev]` や `[pm, dev]`）、`depends_on`（IDのリスト）を持つ。タスクの`roles`を省略した場合は任意の汎用空き枠を消費する。YAML内で`roles`が定義され、CLIでも`--roles`が指定された場合はCLIの指定が優先される。依存先は存在し、循環してはならない。完了済みタスクは完了済みタスクにのみ依存できる。進行中の作業は残作業を表す未完了タスクとして記入する。完了済みタスクは依存関係を満たし、再実行しない。レポートには残期間と経過期間を加えた合計期間を示す。

探索タスクには既存のシナリオ別発見確率を使い、発見した作業は直後の依存先を待たせる。所要期間、レビュー、手戻りも既存の設定に従う。不正なYAML構造入力は、ファイルを明示したエラーにする。`--topology`とともに指定された`--pattern`と`--scale`は警告を表示して無視する。`--continue-from`は併用できない。

`spite simulate --template`は編集可能なYAMLの例を出力する。`--template-resources people`を加えると兼任者の例、`--template-resources roles`を加えると専任者の人数指定例を出力する。`spite simulate --from-git BASE`は`BASE..HEAD`の非マージコミットを1件ずつ完了済みタスクにした下書きを出力する。依存関係や経過期間は推定しない。出力をファイルに保存し、内容を確認して残作業や探索領域を追加する。未コミットの作業や将来の作業は履歴に含まれない。

## モデルの制約と校正

既定ではタスクの所要期間を上限と下限のある三角分布からそれぞれ抽選する。実験的な複雑さ係数を指定すると、プロジェクト全体に相関する変動を加えられる。発見や手戻りは変動を生むが、分布の裾は過去の実績で校正されていない。実際には複数タスクに共通するリスクがある。`predict`と`simulate`の前提は異なり、分位点の比率をそのまま比較することはできない。

過去のプロジェクトや明文化した専門家の前提を使い、プロジェクト全体に共通する係数を検討する。学習に使っていない実績で予測分位点と完了結果を比較し、係数の分布、シナリオ、発見、手戻りへの感度を調べてから既定値を決める。同じリスクを重複して数えないようにする。根拠が得られるまで、新たな係数や校正済みの精度は主張しない。

人数の感度分析では通常人数と倍増後の試行を対応させ、タスク、発見、レビューの試行ごとに共通の乱数を使う。スケジュールの違いは結果に影響し、小さな差は標本誤差の可能性がある。

## 実験的なプロジェクト全体の複雑さリスク

`--complexity-risk`には`off`（既定）、`low`、`medium`、`high`を指定する。各試行で最小値と最頻値が1、最大値がそれぞれ1.25、1.5、2の三角分布から係数を1つ抽選する。発見した作業と手戻りを含むすべての開発タスクの所要期間と、シナリオの発見確率にこの係数を掛ける。発見確率の上限は1とする。レビュー待ちと却下確率は変えない。YAMLの既知タスクやプリセットの初期構造を増やさない。人数比較の対応する試行には同じ係数を使う。

係数の範囲は実績で校正されていない例示的な仮定である。基準に対する上振れのみを表し、他のリスク設定と重複する可能性がある。レポートに選択した水準と範囲を示す。設定は保存され、既存の合成グラフによる継続予測に引き継がれる。`off`で変更を解除できる。

## 実験的なプリセット初期構造の変動

`--topology-variation random`を指定するとプリセットの初期構造を試行ごとに変える。既定は`off`である。直列型と並列型はそれぞれ固定の直列・分岐構造を保つ。複雑型と探索型では直前の最大3ノードから1〜3個の重複しない依存先を選び、統合レビューはすべての末端ノードに依存する。ノード数と種類は変えない。通常人数と人数倍増の対応する試行には同じ初期構造を使う。シードで再現できる。この方法は実験的で、実績による校正はされていない。YAML入力では警告して無視する。設定は合成グラフによる継続予測に引き継がれ、`off`で解除できる。


## 人と役割による資源割り当て（更新）

役割は利用者が自由な粒度で定める担当可能な能力です。YAMLの`people`に一意な`id`と`roles`の一覧を指定すると、1人に複数の役割を持たせられます。`roles: {pm: 1, dev: 1}`は、それぞれ専任者1人ずつを作る簡略指定です。両方をYAMLに同時指定することはできません。CLIの`--roles`はYAMLの指定より優先します。どちらもない場合は従来の`--team-size`を使います。

タスクの各役割には別々の人を同時に割り当てます。兼任者も同じタスクでは1役のみ担当します。役割のないタスクには任意の1人を割り当て、直前の役割は変えません。gateは人員を占有しない待ち時間です。役割は省略、null、空リストにでき、役割を要求することはできません。割り当て不可能なタスクはエラーです。

人が前回と異なる役割を担当すると`--switching-cost`期間を追加します。初回は加算せず、共同タスクでは担当者の切り替えコストの最大値を加算します。発見作業と手戻りは元の作業の役割を引き継ぎます。同時確保は部分的なロックを防ぎますが、公平性は保証しません。人員感度分析では各人の能力を複製します。

### レビュー作業と手戻り先

担当者を占有するレビューは役割付きの`task`、その後の待ちと差し戻し判定は`gate`として表します。gateの`rework_target: build`に上流の`task`または`exploratory`のIDを指定できます。完了済みタスクも指定可能です。差し戻し時は対象の役割を引き継いでその作業を再実行し、gateを再判定します。間のレビュー作業などは再実行しません。省略時は従来の自動選択を維持します。gateの空でない役割指定はエラーです。
