# プロダクト要件定義書 (PRD): シミュレーションモジュール

[English Version](prd.md)

## 1. ビジョンと背景

ソフトウェア開発の納期予測における従来のアプローチには、主に以下の2種類が存在します。
1. **パラメータ分布による近似（現行 Spite のベースライン）**: プロジェクト全体の工期を単一の確率分布（対数正規分布など）でモデル化し、シナリオ（最善・通常・最悪）の違いを主観的な倍率係数で調整する手法。
2. **決定論的ネットワーク計画（PERT / CPM / 静的モンテカルロ法）**: WBS等を用いてプロジェクトを固定の有向非巡回グラフ（DAG）に分解し、各タスクの所要時間のみを確率変数として乱数シミュレーションする手法。

しかし、実際のソフトウェア開発には **Fog of War（戦場の霧）** とも呼ぶべき構造的な不確実性が存在します。
- **未知タスクの動的発見**: 多くの作業（Unknown Unknowns）や隠れた依存関係は、調査・設計・実装を進めて初めて顕在化します。
- **手戻りと反復ループ**: レビュー差し戻し、仕様の不整合、リグレッション障害などにより、単純な非巡回フローではない循環的な手戻りが発生します。
- **レビュー・承認待ちと外部依存**: レビュー待ち、アーキテクチャ承認、顧客確認、外部API提供待ちなど、エンジニアを増員しても短縮できない非線形な待機時間が存在します。
- **並列化の限界**: 直列依存や合流・統合コストによって、チーム人数と工期の関係はアムダールの法則やブルックスの法則に制約されます。

**シミュレーションモジュール**（`/simulation`）は、**Lane-Model** の構想に基づいた構造的シミュレーションエンジンを提供します。固定グラフや恣意的な分布関数を前提とするのではなく、粗い初期条件から仮想プロジェクト構造の集合を動的生成し、リソース制約下での進行をシミュレーションして、共有可能な構造化MarkdownとMermaid図を伴う経験的納期分布を出力します。

## 2. 対象ユーザーと主要ユースケース

### 対象ユーザー
- **エンジニアリングマネージャー / テックリード**: プロジェクトのテールリスクの原因、増員による短縮効果の有無、真のボトルネック箇所を構造的根拠に基づいて説明したいリーダー。
- **アジャイル / スクラムチーム**: スプリントごとに完了実績を固定し、残余の不確実性を再シミュレーションして予測を更新したいチーム。
- **ステークホルダー / 意思決定者**: 最善・通常・最悪シナリオの背後にある前提や妥当性を透明性高く検証したい関係者。

### 主要ユースケース

#### UC-1: 構造的フォワード予測（プロジェクト初期）
プロジェクト開始前に、チームは大まかな前提（規模、不確実性、構造パターン、チーム人数）を指定します。エンジンが最善・通常・最悪シナリオに応じた数千パターンの仮想プロジェクト構造を生成・シミュレーションし、経験的なP50、P80、P90工期を算出します。

#### UC-2: 人員配置・ボトルネック感度分析
チーム人数（例: 1名 vs 2名 vs 4名）を変更した際の工期分位点の変化を比較し、直列依存やレビュー・承認待ちによって並列化の頭打ち（サチュレーション）が発生していないかを検証します。

#### UC-3: スプリントごとの再予測（開発途中）
開発中の経過periodと完了タスク数を累計で記録します。把握している残タスク数から新しい仮の構造を生成します。実際の完了済み依存関係や進行中の作業は再現しません。

#### UC-4: Markdown & Mermaid による共有・レビュー
代表的なプロジェクト構造、クリティカルパス、レビュー・承認のボトルネックを表現したMermaidフローチャートを含む構造化Markdownレポートを出力し、GitのPRやWiki上でテキスト差分としてレビュー・共有します。

## 3. 製品スコープと機能要件

### 3.1. CLIインターフェース: `spite simulate`

シミュレーションエンジンは専用のCLIサブコマンドから実行します。

```bash
uv run spite simulate [OPTIONS]
```

#### 主な入力パラメータ
- `--days-per-period`（正の数、任意）：1 periodに相当する概算日数。カレンダーや祝日は計算しません。
- `--pattern` (選択式: `linear`, `parallel`, `complex`, `exploratory`, デフォルト: `complex`): プロジェクトの基本構造テンプレート。
- `--scale` (選択式: `small`, `medium`, `large`, デフォルト: `medium`): 想定されるおおよそのNode規模。
- `--uncertainty` (選択式: `low`, `medium`, `high`, デフォルト: `medium`): 進行中に隠れたNodeや依存関係が発見される傾向の強さ。
- `--rework-rate` (浮動小数点: `0.0` 〜 `1.0`, デフォルト: `0.15`): レビュー後に手戻りが発生する確率。
- `--team-size` (整数, デフォルト: `2`): 同時に実行可能な並列タスク数の上限。
- `--tasks-per-period`（正の数、既定: `1`）：メンバー1人が1 periodあたりに進めるタスク数の基準。その逆数がタスク期間の最頻値となり、実際の完了数を保証する値ではありません。タスク、発見された作業、手戻りの期間は、この最頻値の0.5〜2倍の範囲とする三角分布から抽選します。レビュー・承認待ちは別の分布を使います。
- `--iterations` (整数, デフォルト: `2000`): シナリオごとのモンテカルロ試行回数。
- `--format` (選択式: `markdown`, `terminal`, `png`, デフォルト: `markdown`): 主たる出力形式。
- `--output`（パス、任意）：実行ごとの`report.md`と`snapshot.json`を保存するルート。PNG形式では`chart.png`も保存します。
- `--continue-from`（実行ID、任意）：保存先ルートから前回のシミュレーションを読み込みます。開始時からの累計`--elapsed-periods`、`--completed-tasks`と、現在把握している`--remaining-tasks`が必要です。残タスクから新しい仮の構造を生成し、完了済みの依存関係や進行中の作業は再現しません。条件は明示的な変更がない限り引き継ぎます。レポートは残期間、合計期間、前回の合計P50・P80・P90を比較します。

---

### 3.2. 構造的グラフ生成モデル

工数のみを確率変数とするのではなく、初期パターンに基づいて動的なプロジェクトグラフ $G \sim P(G \mid X)$ を生成します。

| パターン | 構造的特徴 | 想定される開発シナリオ |
| :--- | :--- | :--- |
| **直線型 (`linear`)** | 順序通りの直列依存 ($A \to B \to C$) と条件付き手戻り | 障害調査、単一トラックでの段階的リファクタリング |
| **並列型 (`parallel`)** | 高い分岐度 ($A \to \{B, C, D\} \to \text{合流}$) | 独立した複数機能の追加、疎結合なマイクロサービス開発 |
| **複雑型 (`complex`)** | ダイヤモンド構造、段階的合流、レビュー、統合テスト | フロントエンド/バックエンド/DBが連動する一般的な複数レイヤー開発 |
| **探索型 (`exploratory`)** | 高いFog of War、動的Node分解、隠れた依存の頻発 | レガシーコード刷新、未知技術のPoC、ゼロイチの新規開発 |

#### シナリオ別の条件設定
- **最善シナリオ (Best)**: 不確実性が低く（未知Nodeの出現が少ない）、手戻り率が極小（5%未満）、レビュー・承認待ちが最短。
- **通常シナリオ (Nominal)**: 入力指定に応じた標準パラメータ。
- **最悪シナリオ (Worst)**: 不確実性が高く（未知Nodeが+50%増加）、手戻り率が高率（25〜40%）、レビュー・承認待ちが長期化。

---

### 3.3. 離散事象・リソースシミュレーションエンジン

生成されたグラフごとに、リソース制約と依存関係を考慮したシミュレーションを実行します。
1. **Node工数のサンプリング**: 各Nodeの所要工数を、複雑度に応じた分布からサンプリング。
2. **リソースキューイング**: 実行可能となったNodeに対し、チーム人数（`--team-size`）の枠をクリティカルパス優先度順に割り当て。
3. **レビュー・承認待ち**: レビュー時に待ち時間が発生します。この待ち時間は開発チームの人員枠を占有しません。確率判定により通過するか、上流作業をやり直すかを決めます。
4. **動的発見**: 探索的Nodeの完了時に確率判定を行い、新たな子Nodeや依存関係を作業グラフへ動的に注入。
5. **完了期間の計測**: 全ての終端Nodeが完了した時点の累計periodを、その試行の所要期間 $T_i$ として記録。

---

### 3.4. 出力仕様と構造化 Markdown レポート

`--format markdown` 指定時、Gitでのバージョン管理やPRへの添付に適した自己完結型のMarkdownレポートを生成します。

1. **エグゼクティブサマリ表**:
   - 最善・通常・最悪シナリオごとのP50（中央値）、P80、P90の期間をperiodで示し、任意で概算日数を併記します。
   - クリティカルパスのボトルネック要約（例: 「レビュー・承認待ち時間がクリティカルパスの32%を占有」など）。
2. **Mermaid による構造可視化**:
   - 代表的な仮想プロジェクト構造を Mermaid の `flowchart LR` / `flowchart TD` で描画。
   - クリティカルパス上のNodeをスタイル強調（`style NodeX stroke:#e74c3c,stroke-width:3px`）し、ボトルネックとなったレビューを視覚化。
3. **経験的分布の表現**:
   - シミュレーション標本から算出した分位点テーブル、通常シナリオのP50・P80・P90の説明、Mermaid `xychart-beta`による分布図。結果は仮定に依存し、実際の完了時期を保証しないことも説明します。
4. **アクションにつながる示唆**:
   - 人員配置に関する感度評価（例: 「直列のレビューが支配的なため、人数を2名から4名に増やしてもP80は6%しか短縮されません」等の示唆）。

## 4. 技術アーキテクチャ

### 4.1. モジュール構成
`/simulation` 機能は `src/spite/simulation/` 配下に実装されます。
- `models.py`: `Node`, `Edge`, `Gate`, `ProjectGraph`, `SimulationResult` などのデータモデル定義。
- `generator.py`: パターンおよびシナリオ設定に基づいて仮想グラフを生成するトポロジー生成器。
- `engine.py`: リソース割り当て、手戻りループ、動的発見を処理する離散事象シミュレータ。
- `reporters/`:
  - `markdown.py`: Markdown および Mermaid ダイアグラム生成器。
  - `terminal.py`: ターミナル向けサマリおよび ASCII レンダラー。
- `cli.py`: Spite CLI 引数パーサーとの統合。

### 4.2. 性能要件
- 3シナリオ × 2,000試行（20〜50 Node規模のグラフ実行計6,000回）が、標準的な開発マシン上で **5秒以内** に完了すること。
- 試行間の不要な中間実行状態を保持せず、メモリ消費量を最小限に抑えること。

## 5. 対象外事項（Non-Goals）とロードマップ

### Phase 1: MVP（本 PRD の対象スコープ）
- 4つの基本パターン（`linear`, `parallel`, `complex`, `exploratory`）によるグラフ生成。
- チーム人数制約および手戻りループを考慮した離散シミュレーション。
- Mermaid図および分位点表を含む構造化Markdownレポート出力。
- CLIサブコマンド `spite simulate` の提供。

### Phase 2: 途中実績の反映と履歴管理（将来拡張）
- 実際のタスクID、依存関係、進行中の状態を取り込んだ再予測。
- 保存した予測を使った精度の事後振り返り。

### Phase 3: 外部システム連携（将来拡張）
- GitHub / GitLab の Issue グラフや PR レビュー実績を解析し、初期パターンのパラメータを自動校正する連携機能。

## ユーザーが指定する構造

`spite simulate --topology FILE`でYAMLを読み込む。ルートには`elapsed_periods`（0以上の数値、省略時0）と`tasks`（リスト）を指定する。各タスクは一意な文字列の`id`、文字列の`name`、`kind`（`task`、`gate`、`exploratory`）、`status`（`pending`、`completed`）、`depends_on`（IDのリスト）を持つ。依存先は存在し、循環してはならない。完了済みタスクは完了済みタスクにのみ依存できる。進行中の作業は残作業を表す未完了タスクとして記入する。完了済みタスクは依存関係を満たし、再実行しない。レポートには残期間と経過期間を加えた合計期間を示す。

探索タスクには既存のシナリオ別発見確率を使い、発見した作業は直後の依存先を待たせる。所要期間、レビュー、手戻りも既存の設定に従う。不正なYAML構造入力は、ファイルを明示したエラーにする。`--topology`とともに指定された`--pattern`と`--scale`は警告を表示して無視する。`--continue-from`は併用できない。

`spite simulate --template`は編集可能なYAMLの例を出力する。`spite simulate --from-git BASE`は`BASE..HEAD`の非マージコミットを1件ずつ完了済みタスクにした下書きを出力する。依存関係や経過期間は推定しない。出力をファイルに保存し、内容を確認して残作業や探索領域を追加する。未コミットの作業や将来の作業は履歴に含まれない。
